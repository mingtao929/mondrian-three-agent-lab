# 蒙德里安几何狂想三 Agent 协作平台产品设计

版本：0.2　日期：2026年11月11日

## 1 产品目标

从零搭建三个 AI agent 共同修复几何画作的实验平台，研究它们在信息不对称环境下如何交换信息、形成共同理解、分工行动并修正错误。游戏参与者固定为 Agent A、B、C；研究者负责配置、观察和分析实验，不参与解题。

保留原任务的画作修复主题、几何平移与旋转、局部信息和共同目标。新增桌面 Agent 接入、实验控制、信息隔离和可回放的过程记录。

## 2 设计依据与确认范围

### 本次原平台观察

已查看火花课堂教师端课程目录及蒙德里安课程详情。课程目录采用白色背景、顶部导航和图片卡片；课程封面使用红黄蓝色块、黑色分割线、白底及几何化中文标题。

课程详情列出四个课时，名称分别为画作修复初体验、画作修复初体验2、画作修复初体验3、画作修复干预体验。说明明确提出三人一组，交流各自信息，利用平移和旋转复原画作，并练习形成共识、分工及沟通策略。

本次尚未进入实际拼图操作页面。游戏内画风、具体关卡、遮挡范围、旋转角度、碰撞规则、提交反馈及干预方式仍需核对。四个课时不等于四个游戏关卡。

### 论文依据

Xu 等（2024），Designing an Online Jigsaw Puzzle Task to Assess Collaborative Problem-Solving Skills，DOI：10.1109/ISEC61299.2024.10664914。论文第3至5页描述三方局部画框、不同碎片、聊天、平移旋转、步数与时间反馈及过程回放。论文中的学生任务验证不直接等同于 AI 协作测量的验证。

### 开源参考

已检索 GitHub，未找到可确认属于论文原平台的公开源码。可参考 PettingZoo 的独立观察、动作和环境更新接口：https://github.com/Farama-Foundation/PettingZoo 。首版借鉴接口思想，暂不引入强化学习训练或大型编排框架。

## 3 游戏与协作机制

三个 agent 面向同一画作目标，各自掌握不同的局部目标信息和所属碎片。局部信息要有互补关系，使交换信息有实际价值。先制作一个可人工验证的小关卡，再增加复杂关卡。

建议首版规则如下，属于本项目设计选择，待规则讨论后确定：

- 三个 agent 使用相同基础模型和任务说明，不预设领导者或检查者角色。
- 每个 agent 可操作自己的碎片，通过公共消息向队友提供信息、询问和提出计划。
- 公开碎片状态与私有目标线索分别定义；目标遮挡不自动意味着隐藏队友动作。
- 使用统一坐标系和明确的旋转规则，避免坐标理解差异掩盖协作问题。
- 首版按轮次调度，每次选择发送消息、执行动作、等待或提交中的一种行为。后续根据研究需要评估异步机制。
- 游戏程序检查动作权限与合法性，更新真实状态；模型不直接修改棋盘或成功结果。
- 成功条件由关卡规则确定；预算耗尽、调用异常和主动停止分别记录，避免混为解题失败。

信息隔离必须在后端生成观察时完成。给 agent 的输入、工具返回和历史消息中均不得包含其无权访问的目标信息或标准答案。提交反馈也应避免成为逐块试探答案的隐蔽通道。

## 4 主要功能与页面

| 页面或模块 | 首版主要功能 |
| --- | --- |
| 实验配置 | 选择关卡，配置三个桌面 Agent 席位、信息条件、通信条件与预算 |
| 实验观察 | 显示拼图状态、当前行动者、消息、动作反馈和剩余预算 |
| 三方视野 | 切换 A、B、C 的实际可见信息，并与研究者全局视野明确区分 |
| 游戏核心 | 管理碎片、平移旋转、操作权限、规则检查与完成判定 |
| Agent 接入 | 向现有桌面 Agent 的独立会话发送局部观察和消息，收集回复并解析动作 |
| 通信与调度 | 管理公共消息顺序、轮次、等待和运行结束条件 |
| 过程回放 | 按事件查看动作前后状态、当时观察和队友消息 |
| 结果导出 | 导出配置、原始事件和基础指标，支持后续分析 |

研究者工作流程：配置实验 → 检查三个初始视野 → 启动 → 观察或暂停 → 查看结果 → 回放与导出。

首版不建设学生账号、班级管理、教师排课、排行榜或复杂关卡编辑器。

## 5 前端画风与交互方向

沿用已观察到的蒙德里安视觉语言：白色或浅灰背景、红黄蓝几何色块、黑色边界。游戏板为视觉主体，实验控制使用克制的样式，避免装饰干扰碎片、遮挡和坐标识别。具体游戏内样式在看到原操作画面后补充。

观察页面建议顶部放关卡与运行控制，中央放棋盘，右侧放公共消息及动作记录，下方提供回放时间线。A、B、C 席位标签和全局视野标签始终可见，防止研究者把自己的全局视野误认为 agent 输入。

碎片同时使用颜色、编号和形状标识；未知区域使用统一遮罩，并区别于可见的白色区域。选中、移动、旋转和非法动作都有明确反馈。暂停与停止含义分开，暂停后可继续。

观察界面的切换不会改变 agent 权限。首版建议模型读取结构化几何状态，界面展示同一状态的图形；视觉模型输入作为后续独立条件，避免首版同时引入视觉识别变量。此选择需在实现前确认。

## 6 实验数据与评价

每次运行保存关卡及规则版本、初始状态、Agent 产品和版本、可见的模型标识与参数、调度顺序和预算。每轮按实验、席位、会话与轮次编号保存平台实际发出的完整输入（任务提示、局部观察、可见消息和上一轮反馈）与桌面 Agent 返回的原始回复。解析后的动作、执行结果、状态变化、耗时、错误和可获得的 token 用量另存。解析失败或超时也保留已收到的内容。

上述原始记录覆盖平台与 Agent 的接口。若桌面应用追加系统提示、压缩历史或在内部多次调用模型，只有其官方接口明确提供的内部输入输出才可另行记录。导出时注明覆盖范围及缺失字段。日志仅经研究者通道读取，排除登录凭据和平台认证令牌。

回放重用已保存的事件，不重新调用模型。保存配置可以支持重复实验，但不能保证外部模型每次输出完全相同。

| 评价维度 | 研究用途 |
| --- | --- |
| 完成情况与动作数 | 判断是否解决任务及执行效率 |
| 信息请求与回应 | 观察信息缺口是否被识别和填补 |
| 共享信息后的行动 | 检查队友是否采用收到的信息 |
| 冲突与纠错事件 | 分析协商和错误修复方式 |
| 调用量与耗时 | 衡量协作资源成本 |

先保留原始证据，再制定人工编码规则；不把消息数量或模型自述直接等同于协作质量，也不默认生成自动 CPS 总分。

后续优先比较信息不对称下允许通信和禁止通信的条件，再增加信息对称条件。各对照使用匹配关卡与预算，轮换席位和行动顺序，并进行重复运行。禁止通信的表现下降也可能来自线索不足，须结合关卡可解性解释。

## 7 分步搭建与验收

| 步骤 | 交付物 | 验收重点 |
| --- | --- | --- |
| 1 规则与样例关卡 | 小关卡说明和三方信息分配 | 全局有解，局部信息互补，规则无歧义 |
| 2 游戏核心 | 不依赖模型的状态与动作程序 | 平移旋转、边界、权限和完成判定正确 |
| 3 信息与通信 | 三方观察和消息模块 | 私有信息无泄露，消息顺序明确 |
| 4 脚本联调 | 三个脚本席位完成操作流程 | 状态更新一致，事件可还原 |
| 5 桌面 Agent 接入 | 先验证一个桌面会话的收发和记录，再扩展为三个独立会话 | 原始输入输出可对照，动作可解析，会话互不串线 |
| 6 前端观察 | 棋盘、视野切换和事件面板 | 显示内容与真实状态一致 |
| 7 回放与对照 | 回放、导出和基础实验条件 | 记录完整，可追溯到当时输入及结果 |

技术建议为 Python 游戏核心与轻量网页界面，具体依赖在实现前确定。每次只交付一个可理解的小步骤：解释目的，展示带中文注释的代码，补充相关测试，验证通过后提交 Git commit。

### 单容器部署与桌面连接

网站前端、游戏后端、调度与日志存储运行在一个 Docker 容器内。桌面 Agent 在宿主机运行，由轻量适配程序通过受限接口收发。优先使用产品提供的官方接口或支持 ACP 的接入方式。若目标应用是 Codex，可核对其 App Server 的会话与事件支持，并验证现有客户端的可用能力。若应用只支持界面操作，先以单席位验证发送、完成识别与回复读取，再判断能否稳定自动运行。参考 [ACP 会话协议](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v1/prompt-turn.mdx) 和 [Codex App Server](https://github.com/openai/codex/tree/main/codex-rs/app-server)。

Docker 提供容器边界，三席位的信息隔离由游戏后端执行。每席位单独认证，仅可取自身观察、读获准消息并提交自身动作。完整关卡、答案、日志和研究者视图使用独立权限。容器不挂载宿主项目目录或 Docker socket，数据使用专用卷，端口默认绑定本机。参考 [Docker Engine 安全说明](https://docs.docker.com/engine/security/)。

宿主桌面 Agent 的文件、浏览器和终端工具可能绕过接口隔离。实验会话需使用独立工作区、最小工具权限及彼此独立的上下文，且无法访问 Docker 管理权限、研究者浏览器会话和完整关卡数据。若某应用无法限制这些能力，可用于联调，正式实验应选择可限制权限的接入方式。

接入验收时检查 A 不能读取 B/C 的私有观察或研究者数据，拒绝越权操作，并确认每个有效或失败回合都能对应原始输入输出与最终动作。

## 8 实现前待确认

1. 原游戏实际操作画面与规则，以及是否需要精确复现原关卡。
2. 首版是否采用结构化输入，后续再单独接入视觉输入。
3. 现有桌面 Agent 的产品、版本及接入能力。确认需要记录平台可见的完整交互，还是还需要应用内部每次模型调用的输入输出。
4. 首版轮次通信是否符合目标研究，是否需要另设自由通信阶段。
